# CampusHub User Service

The **User Service** of CampusHub, a university management platform built as Spring Boot
microservices. It owns user accounts, authentication (email + password, JWT), the three roles and
user profiles. The other CampusHub services (Academic, Grade, Request, Announcement) have their
own databases and refer to users only by id; see
[docs/CAMPUSHUB_IDENTITY_CONTRACT.md](docs/CAMPUSHUB_IDENTITY_CONTRACT.md).

- Spring Boot 3.5.6, Java 17, Spring Security, stateless JWT (JJWT 0.12, HS256)
- MySQL 8.4 with Spring Data JPA and Flyway
- BCrypt passwords, role-based authorization, Swagger UI

## Roles and accounts

| Role         | Who creates it                                   | Role-specific attribute        |
|--------------|--------------------------------------------------|--------------------------------|
| `ETUDIANT`   | the student (registration) or an administrator   | `matricule` (generated)        |
| `ENSEIGNANT` | an administrator only                            | `specialite`                   |
| `ADMIN`      | an administrator only (first one: bootstrap)     | `service` (department)         |

Every user has: `id` (UUID), `nom`, `prenom`, `email`, a BCrypt password, `role`, `status`,
`createdAt`.

Account statuses:

| Status             | Meaning                                                       | Can log in |
|--------------------|---------------------------------------------------------------|------------|
| `PENDING_APPROVAL` | a self-registered student waiting for an administrator        | no         |
| `ACTIVE`           | normal account                                                | **yes**    |
| `SUSPENDED`        | blocked by an administrator, can be reactivated               | no         |

### Student approval workflow

1. The student calls `POST /api/v1/auth/register` with nom, prenom, email and password. No email
   is sent and there is no confirmation step. The account is `ETUDIANT` / `PENDING_APPROVAL`,
   whatever else the request contains.
2. Logging in now answers **403** "Your registration is awaiting approval by an administrator".
3. An administrator lists pending registrations (`GET /api/v1/admin/users?status=PENDING_APPROVAL`)
   and approves one (`PATCH /api/v1/admin/users/{id}/approve`).
4. Approval generates the **matricule** and sets the account to `ACTIVE` in one transaction.
5. The student can log in.

**Matricules** look like `ETU20260001`: `ETU`, the year of approval, then a number that restarts
at 1 each year. They are generated by the database, never typed by hand, and can't be edited.
Each year has one row in `matricule_counters`. Approval increments it with
`INSERT ... ON DUPLICATE KEY UPDATE last_number = last_number + 1`, which locks the row until the
approval commits. Two approvals at the same moment therefore always get different numbers, and
the `UNIQUE` constraint on `users.matricule` is the final safety net. This was tested with 200
concurrent generations on MySQL 8.4.

### Rules that protect against privilege escalation

- Public registration can only create a pending `ETUDIANT`; `role`/`status`/`matricule` in the
  request are ignored.
- `PUT /api/v1/users/me` changes only nom and prenom.
- Every `/api/v1/admin/**` endpoint requires `ROLE_ADMIN` (checked in `SecurityConfig` and again
  with `@PreAuthorize`).
- An administrator cannot change their own role or status.
- A role-specific attribute is only accepted for its own role. The database refuses the
  inconsistent rows too (CHECK constraints).
- No response ever contains the password hash.

## Authentication flow (JWT)

1. `POST /api/v1/auth/login` with email + password returns an access token (valid 1 hour by
   default, `JWT_ACCESS_TOKEN_TTL`).
2. The client sends `Authorization: Bearer <token>` on every request.
3. `JwtAuthenticationFilter` checks the signature, the issuer (`campushub-user-service`) and the
   expiry. It then re-reads the user, who must still be `ACTIVE`, still have the role in the
   token, and must not have changed their password since the token was issued.

Token claims: `sub` (user id), `role`, `iss`, `iat`, `exp`, `jti`. Never a password or personal
data.

**There is no refresh token.** When the access token expires, the user logs in again. There is
no logout endpoint either: logging out means the client discards its token.

**Effect on already-issued tokens:** in this service a suspension, a role change or a password
change takes effect on the very next request, because the filter checks the database. Other
CampusHub services that only verify the token signature keep accepting an old token until it
expires (at most `JWT_ACCESS_TOKEN_TTL`). See the identity contract.

Errors use one JSON format: `401` without a valid token, `403` when the role isn't allowed:

```json
{ "timestamp": "2026-10-15T10:00:00Z", "status": 403, "code": "FORBIDDEN",
  "message": "You do not have permission to perform this operation", "fieldErrors": [] }
```

Login, registration and password change are rate-limited per client (in memory, 10 / 5 / 5
attempts per 15 minutes by default), then answer `429`.

## API

Base URL `http://localhost:8081`. Swagger UI: `http://localhost:8081/swagger-ui.html`.

| Method & path                               | Access        | Purpose |
|---------------------------------------------|---------------|---------|
| `POST /api/v1/auth/register`                | public        | Student registration (pending) |
| `POST /api/v1/auth/login`                   | public        | Get an access token |
| `GET /api/v1/users/me`                      | any role      | Own profile |
| `PUT /api/v1/users/me`                      | any role      | Update own nom/prenom |
| `PUT /api/v1/users/me/password`             | any role      | Change own password (then log in again) |
| `GET /api/v1/admin/users?role=&status=&page=&size=` | ADMIN | List users, newest first (size ≤ 100) |
| `GET /api/v1/admin/users/{id}`              | ADMIN         | One user |
| `POST /api/v1/admin/users`                  | ADMIN         | Create a user of any role (active immediately) |
| `PUT /api/v1/admin/users/{id}`              | ADMIN         | Edit nom, prenom, email, specialite/service |
| `PATCH /api/v1/admin/users/{id}/role`       | ADMIN, not self | Change role |
| `PATCH /api/v1/admin/users/{id}/status`     | ADMIN, not self | `SUSPENDED` or `ACTIVE` (reactivate) |
| `PATCH /api/v1/admin/users/{id}/approve`    | ADMIN         | Approve a pending student |
| `GET /actuator/health`                      | public        | Health check |

Notes:
- A role change clears the previous role's attribute; becoming `ETUDIANT` generates a matricule.
  The role of a registration still awaiting approval can't be changed (approve it first).
- On `PUT /api/v1/admin/users/{id}`, an omitted `specialite`/`service` keeps its value and `""`
  clears it.
- Additional administrators are created at any time by an existing administrator with
  `POST /api/v1/admin/users` and `"role": "ADMIN"`. The `service` (administrative department) is
  required, and the account is `ACTIVE` immediately.

### Sample requests

Register:

```http
POST /api/v1/auth/register
Content-Type: application/json

{ "nom": "Martin", "prenom": "Alice", "email": "alice@univ.example", "password": "alice-password-123" }
```

```json
HTTP/1.1 201 Created

  "createdAt": "2026-10-15T09:30:00.123456Z" }
```

```http
PATCH /api/v1/admin/users/3f2b8c1e-5d4a-4c1b-9a0e-2d7f6b1c8e90/approve

```

```json
HTTP/1.1 200 OK

  "prenom": "Alice", "role": "ETUDIANT", "status": "ACTIVE", "matricule": "ETU20260001",
  "createdAt": "2026-10-15T09:30:00.123456Z" }
```

Login:

```http
POST /api/v1/auth/login
Content-Type: application/json

{ "email": "alice@univ.example", "password": "alice-password-123" }
```

```json
HTTP/1.1 200 OK
{ "accessToken": "eyJhbGciOiJIUzI1NiJ9...", "tokenType": "Bearer", "expiresInSeconds": 3600 }
```

Create a teacher:

```http
POST /api/v1/admin/users
Authorization: Bearer <admin token>
Content-Type: application/json

{ "email": "jean.dupont@univ.example", "password": "teacher-password-123", "role": "ENSEIGNANT",
  "nom": "Dupont", "prenom": "Jean", "specialite": "Informatique" }
```

Suspend, then reactivate:

```http
PATCH /api/v1/admin/users/{id}/status
Authorization: Bearer <admin token>
Content-Type: application/json

```

## Prerequisites

- **Java 17** (`JAVA_HOME` pointing to it)
- **Maven**: not needed, use the bundled wrapper (`mvnw` / `mvnw.cmd`, Maven 3.9.9)
- **MySQL 8.4 LTS** server, only to run the application (the default tests don't need it)

## MySQL configuration

The service uses its **own** database, `campushub_users`. It never uses the old H&B Travel
database: Flyway refuses to start on a database whose migration history isn't CampusHub's
(checksum mismatch), and won't adopt a non-empty database without a history
(`baseline-on-migrate: false`).

Create the database and an application user once, as `root` in a MySQL client:

```sql
CREATE DATABASE campushub_users
  CHARACTER SET utf8mb4
  COLLATE utf8mb4_0900_ai_ci;

-- Choose your own strong password; don't commit it anywhere.
CREATE USER 'campushub_app'@'localhost' IDENTIFIED BY '<your-strong-password>';

-- Flyway creates the tables, hence the DDL rights. Scoped to this database only.
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX, REFERENCES
  ON campushub_users.* TO 'campushub_app'@'localhost';
```

Flyway creates the tables at first startup:

- `V1__create_users.sql`: the `users` table
- `V2__create_matricule_counters.sql`: the yearly matricule counters

Never edit an applied migration; add a `V3__...` instead.

## Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `DB_PASSWORD` | **none (required)** | password of `campushub_app` |
| `DB_HOST` / `DB_PORT` / `DB_NAME` / `DB_USERNAME` | `localhost` / `3306` / `campushub_users` / `campushub_app` | connection |
| `DB_URL` | built from the above | full JDBC URL instead (keep the UTC parameters) |
| `JWT_SECRET` | none (a public dev value on the `local` profile only) | JWT signing key, ≥ 32 bytes |
| `JWT_ACCESS_TOKEN_TTL` | `PT1H` | token lifetime |
| `CAMPUSHUB_ADMIN_EMAIL` / `CAMPUSHUB_ADMIN_PASSWORD` | empty | first administrator (see below) |
| `CORS_ALLOWED_ORIGINS` | `http://localhost:3000` (local) | frontend origin(s) |
| `SERVER_PORT` | `8081` | HTTP port |
| `SPRING_PROFILES_ACTIVE` | `local` | Spring profile |

See [.env.example](.env.example). If `DB_PASSWORD` is missing, startup stops with a message
naming the variable to set.

**First administrator.** No endpoint creates administrators publicly. For the very first one, set
`CAMPUSHUB_ADMIN_EMAIL` and `CAMPUSHUB_ADMIN_PASSWORD` (12+ characters) before starting. At
startup the service creates that administrator only if no administrator exists yet. It never
modifies an existing account and never logs the password. You can unset the variables afterwards.
Further administrators are created through `POST /api/v1/admin/users`, never by the bootstrap.

> **Changing `CAMPUSHUB_ADMIN_PASSWORD` later has no effect.** Once an administrator exists, the
> startup log says `Admin bootstrap skipped: an administrator already exists`. The stored
> password stays the one the variable held on the very first start, so logging in with the new
> value gives 401.

### Recovering the first administrator's password (local development only)

This resets the password of one existing administrator in place. Nothing is deleted, and the
service can keep running.

1. Save this helper **outside the project** (e.g. `%TEMP%\HashPassword.java`). It hashes with
   the same `BCryptPasswordEncoder` as the service (`SecurityConfig`) and reads the password from
   `CAMPUSHUB_ADMIN_PASSWORD`, so it never appears on the command line:

   ```java
   import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;

   public class HashPassword {
       public static void main(String[] args) {
           String password = System.getenv("CAMPUSHUB_ADMIN_PASSWORD");
           if (password == null || password.length() < 12 || password.length() > 128 || !password.equals(password.strip())) {
               System.err.println("CAMPUSHUB_ADMIN_PASSWORD must be set: 12-128 characters, no leading/trailing spaces.");
               System.exit(1);
           }
           BCryptPasswordEncoder encoder = new BCryptPasswordEncoder();
           String hash = encoder.encode(password);
           if (!encoder.matches(password, hash)) throw new IllegalStateException("Hash self-check failed");
           System.out.println(hash);
       }
   }
   ```

2. From the project folder (PowerShell), print the hash:

   ```powershell
   $env:CAMPUSHUB_ADMIN_PASSWORD = "<the new password, 12+ characters>"
   .\mvnw.cmd -q dependency:build-classpath "-Dmdep.outputFile=target\cp.txt" "-Dmdep.includeScope=compile"
   java -cp (Get-Content target\cp.txt) "$env:TEMP\HashPassword.java"
   # -> $2a$10$...  (60 characters)
   ```

3. In a MySQL client connected as `root` (or `campushub_app`), paste the hash between **single
   quotes**:

   ```sql
   USE campushub_users;
   UPDATE users
      SET password_hash = '<paste the $2a$10$... hash>', updated_at = UTC_TIMESTAMP(6)
    WHERE email = '<admin email>' AND role = 'ADMIN';
   -- Must report: 1 row affected. If 0, check the email.
   ```

4. Log in with the new password. Then delete `HashPassword.java` and `target\cp.txt`.

## Running

PowerShell:

```powershell
$env:DB_PASSWORD = "<your-strong-password>"
$env:CAMPUSHUB_ADMIN_EMAIL = "admin@univ.example"        # first run only
$env:CAMPUSHUB_ADMIN_PASSWORD = "<a-12+-char-password>"  # first run only
.\mvnw.cmd spring-boot:run
```

Bash:

```bash
export DB_PASSWORD='<your-strong-password>'
./mvnw spring-boot:run
```

Then open `http://localhost:8081/swagger-ui.html`, or check `http://localhost:8081/actuator/health`.

Build a jar: `.\mvnw.cmd clean package`, then `java -jar target/campushub-user-service-0.0.1-SNAPSHOT.jar`.

## Tests

```powershell
.\mvnw.cmd test                 # fast suite, no database needed
.\mvnw.cmd test -Pmysql-verify  # against the real MySQL database (needs DB_PASSWORD)
```

- The fast suite runs the real Spring Security filter chain, controllers and services, with the
  repository mocked.
- `-Pmysql-verify` runs `MySqlVerificationTest`. It checks:
  - the MySQL version and UTC session;
  - the Flyway history;
  - that Hibernate's mapping matches the schema;
  - the CHECK and UNIQUE constraints;
  - 200 concurrent matricule generations.

  It cleans up its own rows and uses the counter year 2999, so it never consumes real matricule
  numbers.

## Known limitations

- Already-issued tokens stay valid in **other** services until they expire after a suspension,
  role change or password change. This service itself rejects them immediately.
- The JWT key is a shared HMAC secret: any service that holds it to verify tokens could also sign
  them. Switching to RS256 with a public key is the next step if that matters.
- The rate limiter lives in memory, so it holds for one instance only.
- There is no password reset by email (no mail service). An administrator can't reset a password
  either today. A forgotten password currently needs a new account or a manual database fix.
